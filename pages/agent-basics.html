AI Agent 怎麼運作

代理迴圈、工具呼叫與上下文

查證日期：2026-09-16。方案與功能變動快，請以官方最新說明為準。

你跟 ChatGPT 或 Claude 網頁版聊天時，發生的事情很單純：你打字、模型回一段文字、結束。這頁要講的是另一種東西，叫「agent」（代理），中文教材常譯「AI 代理」。它跟聊天機器人的差別在於多了工具，跟一個會反覆執行的迴圈。搞懂這個差異，才看得懂後面 SKILL、MCP、Subagent 這些機制到底在解決什麼問題。

一、聊天機器人跟 agent，差在哪裡

聊天機器人只做一件事：讀你的訊息，輸出文字。它看不到你的檔案，也不能真的去執行任何動作，你要它「幫我查一下這個檔案有沒有錯字」，它只能憑你貼給它的內容回答，貼多少，它就只看得到多少。

Agent 多了兩個東西：工具跟迴圈。Claude Code 的官方文件把這句話講得很直接：「沒有工具，Claude 只能用文字回應；有了工具，Claude 可以真的動手：讀你的程式碼、編輯檔案、執行指令、搜尋網路、串接外部服務」[1]。工具讓模型從「只會講」變成「能夠做」；迴圈則讓它一步接一步做下去，而不是回一次就結束。

官方把這個迴圈拆成三個階段：蒐集脈絡（gather context）、採取行動（take action）、驗證結果（verify results）。這三個階段會交錯進行，不是死板的三步驟，模型會依照上一步學到的東西，決定下一步該做什麼，一路串起十幾個動作，中途發現方向不對還會自己修正[1]。

走一遍實際例子

假設你對一個代理型工具說：「幫我找出這個專案裡所有失效的連結並修好。」它大概會這樣走：

  1. 蒐集脈絡：先搜尋專案裡所有的 Markdown 檔案，抓出裡面每一個連結語法。
  2. 蒐集脈絡：逐一比對每個連結指向的檔案是不是真的存在，列出一份失效連結清單，包含檔名與行號。
  3. 採取行動：對清單裡的第一個失效連結，去找可能是哪個檔案被改名或搬移了。
  4. 驗證結果：確認找到的新路徑是對的（例如檔名對得起來、內容也對得上主題），不是隨便找一個相似名字的檔案套進去。
  5. 採取行動：把連結改成新路徑。
  6. 重複第 3 到第 5 步，直到清單跑完。
  7. 驗證結果：重新掃描一次整個專案，確認沒有殘留的失效連結；如果專案有建置流程，順便跑一次建置，看看有沒有因為改連結弄壞別的東西。
  8. 遇到「找不到對應的新檔案，也看不出原本連去哪裡」這種情況，它會停下來問你，不會隨便猜一個答案填上去。

這整個過程你只下了一句指令，剩下的步驟都是它自己決定的：要不要先列清單、要不要每改一個就驗一次、遇到不確定的情況要不要問你。聊天機器人做不到這件事，因為它連你的專案資料夾長什麼樣子都看不到。

二、上下文視窗：為什麼會滿，滿了會怎樣

上下文視窗（context window）是模型這一次能同時看到的所有內容：你的對話紀錄、它讀過的檔案、它跑過的指令輸出、系統指示、已載入的規則檔案，全部加起來的總量[2]。這個視窗是有限的，跟人的記憶力有限是一樣的道理，不是模型「不想記」，是塞不進去。

為什麼會滿？兩個原因加在一起。一是視窗本身有上限，做得越多、讀得越多，累積的內容自然越多；二是模型的注意力機制本身，讓內容越長，模型從中間精準抓出某一句話的能力越弱，官方研究稱這個現象是「context rot」：隨著視窗裡的 token 數增加，模型從中準確回想資訊的能力會下降，而且是漸進式的衰退，不是忽然斷崖式失憶[3]。舉例來說，一場很長的對話裡，你在最前面交代過「不要動 data/raw/ 資料夾」，這類早期講過的限制條件，到對話後段就可能被模型忽略，不是它故意不聽，是回想的準確度已經隨著內容變長而下降。

滿了之後會發生什麼事？Claude Code 會自動處理，但代價是舊資訊可能被犧牲：「它會先清掉比較舊的工具輸出，需要的話再把整段對話做摘要。你的原始需求跟關鍵程式碼片段會被保留，但對話早期的詳細指示可能會遺失」[2]。這也是為什麼官方建議把「一定要記住的規則」寫進 CLAUDE.md 這類常駐檔案，不要只講一次就指望它記得，對話一旦被摘要壓縮過，早期講的細節本來就有可能保不住[2]。

那「新開一個對話」跟「等它自動壓縮」有什麼不同？壓縮（compaction）是在同一個對話裡，把舊內容摘要濃縮之後繼續用同一個上下文；新開一個對話（Claude Code 裡是新的 session）則是完全重置，帶著全新的上下文視窗，不記得上一個對話的任何細節，除非你自己把重點寫進 CLAUDE.md 或機制上自動累積的記憶檔案裡[2][4]。官方對「一直反覆修正同一個錯誤，卻越改越糟」這種情況的建議，正是新開一個對話重新開始，而不是在已經被錯誤答案汙染過的上下文裡繼續修。這代表新開對話有時候是止血的辦法[4]。

三、工具權限與沙箱：為什麼要先問過你

Agent 能真的去改你的檔案、跑你的指令，這正是它最有價值也最危險的地方。兩家主要的代理型工具都用「先問過你」當預設防線，只是問的方式跟切法不太一樣。

Claude Code 的 permission modes

官方文件目前列出六種 permission mode，但 Shift+Tab 只在其中三種之間循環（default → acceptEdits → plan → default），其他幾種要另外設定或啟用之後才會加入。官方原文提醒「不是每種模式都在預設循環裡」（"Not every mode is in the default cycle."）[5][8]：

模式 行為 在 Shift+Tab 循環裡嗎
default（介面顯示 Manual） 每次要編輯檔案或跑指令都先問你 是，循環起點
acceptEdits 編輯檔案跟常見的檔案系統指令（mkdir、mv 之類）自動放行，其他指令仍會問 是
plan 只讀檔、只探索，不動你的原始檔案 是
auto 背景有一個分類器幫你先審過大部分動作，只擋下真正危險的 只有這個功能對你的方案可用時才會加進循環
dontAsk 原本要問你的動作直接拒絕，只執行已經核准的工具 不會，永遠要另外設定
bypassPermissions 完全跳過詢問；官方警告只該在容器或虛擬機這類隔離環境使用，因為連 .git、.claude 這類受保護路徑也會一起放行 預設不在循環裡，要先用 --permission-mode bypassPermissions 之類的旗標或設定啟用，啟用後才會插進 plan 之後

設定檔（settings.json）裡還可以更細緻地指定 allow／ask／deny 規則。這幾種更進階的設定寫法，見Claude Code 設定總覽。

Codex 的 sandbox modes

Codex 用三段式的沙箱模式決定它能碰到什麼[6]：

模式 能做什麼
read-only 只能檢視，不能改任何東西
workspace-write（本機預設） 可以在你指定的工作區內編輯檔案、跑指令
danger-full-access 移除所有檔案系統與網路邊界，等於完全不設防

搭配沙箱模式的是核准政策（approval policy），預設是 on-request：Codex 遇到超出目前沙箱範圍的動作，會停下來問你[6]。

兩家工具的邏輯其實一致：風險越高的動作，越需要人在場核准，差別只在於「用一個分類器幫你先篩一輪」還是「用固定的三段式沙箱切好邊界」。

四、workflow 跟 agent，官方怎麼分

「workflow（工作流程）」跟「agent（代理）」這兩個詞常被混用，Anthropic 在〈Building effective agents〉裡給了明確定義：workflow 是「LLM 與工具依照預先寫好的程式路徑被協調運作的系統」；agent 則是「LLM 動態指揮自己的流程與工具使用方式，自己掌控要怎麼完成任務的系統」[7]。

用白話說：workflow 是你事先規劃好先做 A、再做 B、最後做 C，模型只是照著這條路走；agent 是你只講目標，模型自己決定要先做 A 還是先做 B，做完 A 發現不對，自己改去做 D。前面「找失效連結」的例子，就是後者，沒有人事先寫好「第一步搜尋、第二步比對」，是模型自己拆解出這個順序的。

Anthropic 也提醒，agent 要能自主運作，關鍵是每一步都要能從環境裡拿到「真實回饋」，例如工具呼叫的結果或程式碼的執行輸出，用這些回饋確認自己的進度，不是憑自己「感覺應該做完了」就結束[7]。這正是本站另一頁〈把 AI 代理的工作環境設計得可靠〉要處理的問題：怎麼確保這個回饋機制是可信的，不是自己騙自己。

五、代理迴圈：文字版流程

本頁原本想用流程圖表示這個迴圈，但這個網站的建置工具（build.py）沒有載入任何圖表渲染的程式庫，貼上流程圖語法只會變成一段看不出圖形的原始文字，所以改用條列式說明：

  1. 你下一個指令或目標。
  2. Agent 蒐集脈絡：讀檔、搜尋、查看目前狀態，弄清楚現在的情況是什麼。
  3. Agent 採取行動：呼叫工具，例如編輯檔案、執行指令、查資料。
  4. 工具回傳結果，變成新的脈絡，回到步驟 2 或直接進入步驟 5。
  5. Agent 驗證結果：跑測試、重新讀一次檔案、對照原本的目標，確認做對了沒有。
  6. 沒做完或做錯了，回到步驟 2 或 3 繼續；你隨時可以在任何一步插話，改變方向或補充資訊。
  7. 確認任務完成，結束這一輪，把結果回報給你。

這個迴圈會一直重複，直到任務完成或你叫它停下來為止[1]。
